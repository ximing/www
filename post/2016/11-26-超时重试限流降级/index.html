第 12 篇结尾预告过这一篇。写作时是 2016 年 11 月底，IM 融合切流已完成数月，云盘服务端从单人维护发展到几十台机器，承接大象的全量文件流转。

开始做 Java 服务端前，我已有 Node.js、C# 等后端经验。已有经验能帮助预判问题，却不能直接给出 Java 项目的答案：Node.js 的事件循环和 Java 的请求线程不同，单机状态扩展到多实例后也会改变约束。系列中的学习顺序因此并不完全跟随故障发生顺序。我会根据项目可能遇到的并发、资源耗尽、下游失败和容量问题提前补课，再把确认适用的做法用于项目；遇到实际问题后，再用日志、压测和线上现象核对假设。本文把系列中分散出现的可用性措施放在一起，说明它们分别处理什么问题，以及当时仍未解决什么问题。

四项措施分别处理的失败条件

第 9 篇算过一笔账：如果一条四跳链路中各跳相互独立，且每跳成功率均为 p，整条链路的成功率是 p⁴；每跳 99.99%，整链约为 99.96%。这笔计算说明了从数据面移除 Java 中转的原因，也说明需要逐段分析失败原因。

当时主要需要处理四类情况：

  • 下游长期无响应，调用线程持续等待，线程池容量被占满；
  • 下游短暂抖动，例如网络闪断、一次 GC 停顿或实例重启；
  • 请求量超过当前容量，排队时间和超时比例同时上升；
  • 非关键路径，例如上报、通知或聚合字段，变慢后占用关键路径的资源。

超时、重试、限流和降级分别覆盖不同的失败条件。跨进程调用应设置可传播的截止时间；重试应有次数上限、退避和抖动，并以幂等性为前提；入口和资源池都需要过载保护；非关键功能需要预先定义降级结果。缺少其中任一项，故障的影响范围可能扩大。这些措施也无法保证请求一定成功。

超时：为调用设置截止时间

客户端的超时默认值不能靠经验假设。不同 HTTP 客户端、JDBC 驱动和版本对未配置值及 0 的语义不同，有的表示无限等待，有的使用组件默认值。上线前应显式检查实际使用组件的连接、读取和查询超时配置。若下游不返回，调用线程可能阻塞在 socket read 或驱动调用中；共享线程池会因此耗尽，独立线程池只能把影响限制在对应资源池。

在整理跨进程调用时，云盘要求每次调用先确定最多等待多久。无法给出时间预算的调用不应上线。

第 5 篇提到，Future.get 的超时只会让等待方结束等待，cancel(true) 也不保证能中止已执行的任务。下游调用自身仍需有超时。一个调用通常涉及三类时间限制：

  • connect 超时限制建立连接的等待时间。它只覆盖连接建立，不表示对端应用一定可用；
  • read 或请求超时限制等待响应数据的时间。具体覆盖范围取决于客户端实现；
  • Future.get 或上层请求的截止时间限制聚合接口整体还愿意等待多久，并应覆盖线程池排队、下游调用和结果合并。

这些限制应使用同一个请求预算推导，而不是各自独立配置。串行调用的时间上限接近各阶段预算之和，并行调用受最长关键路径影响；上层截止时间应为下游调用保留取消、降级和响应序列化的时间。只设置 Future.get 超时会让上层提前返回，而底层任务、连接或线程仍可能继续占用资源。

超时值应参考下游延迟分位数、压测结果和接口总预算。第 10 篇的压测与线上分位数可作为当时的输入，但 P99 加固定余量不是通用公式：流量、依赖状态和网络路径变化后需要复核。首页类接口的体验预算在当时约为一秒。超时触发后，调用方能在有限时间内得到明确错误，限流或降级才有机会继续处理该请求。

重试：先确认幂等性和失败阶段

短暂故障可能通过重试恢复，但重试会增加下游负载。接口层重试一次、客户端因超时再重试一次，会把一次用户操作放大为多次真实请求。下游处于恢复期时，这种放大会提高排队和超时比例，形成重试风暴。第 11 篇缓存 key 失效时，数据库已在处理回源流量，自动重试会进一步增加压力。

云盘当时的规则是，同一接口对同一依赖最多重试一次，首次请求共两次；重试间隔递增；只重试具备幂等保障的操作。生产实现还应为退避增加上限和随机抖动，避免大量请求在相同时间再次发出。原有记录只写了递增间隔，未说明是否实现了抖动。

读操作通常更容易满足幂等条件，但仍要确认它没有触发计费、访问计数或其他副作用。写操作即使超时，也可能已经在服务端执行成功，因此不能仅按异常类型判断是否安全重试。第 6 篇的“消息唯一键 + 去重表”处理消费端重复投递，第 12 篇的“客户端操作 ID + 唯一键”处理写路径的重复提交。有这类去重机制后，写操作才能在重复提交时得到可预期的结果；没有幂等键或去重约束时，应返回不确定结果或让调用方查询状态，而不是直接重试。

参数错误、权限不足等业务性 4xx 不应重试。连接失败也要区分发生在请求发送前还是发送后：前者通常可按幂等规则重试，后者仍可能导致服务端已处理请求。本文当时的口径是只对超时和明确的连接类异常重试，其余失败原样上抛；这个口径缺少对请求是否已送达的判断，仍依赖操作本身的幂等保障。

当时没有支持重试时切换到健康实例的机制。负载均衡的具体行为会决定重试是否仍落到故障实例，不能假定重试一定会换实例。

限流：入口和资源池的过载保护

云盘的限流分为两层。

**外层是入口计数限流。**第 2 篇慢查询事故中的入口限流，后来成为标配：入口按接口统计秒级请求数，使用单机内存中按秒重置的计数器。超过阈值的请求直接返回“系统繁忙”，不再进入线程池。阈值参考第 10 篇压测得到的单机容量拐点，并保留安全余量。

这种固定窗口计数器实现简单，但在窗口边界可能允许短时间突发超过单秒阈值，也不能直接反映正在执行的并发请求数。它适合在入口快速拒绝明显超量的流量。需要控制突发、平滑速率或按用户配额时，应使用能表达这些约束的限流算法和存储方案。

**内层是线程池拒绝策略。**第 2 篇将队列改为有界队列，并使用 AbortPolicy 快速失败。有限队列和拒绝策略是资源池的过载保护：它限制进入该线程池的排队与执行量，但不等同于按时间窗口计算的限流。两者应配合使用，入口限制到达速率，线程池在容量耗尽时拒绝请求。

线程池隔离还需要和连接池上限一起设计。每个下游依赖应有明确的并发、队列和连接数预算，避免某个慢依赖占满共享线程、数据库连接或 HTTP 连接；池大小也不能只按 CPU 核数设置，因为阻塞等待和连接数都会改变可承受的并发度。

计数限流是单机口径。全站阈值会随实例数变化，扩缩容后需要重新核对单机阈值、负载分配和总容量。真正的全局限流需要共享状态或集中式配额服务，当时没有实现。原因是需要引入共享计数依赖，当时优先目标是保护单机并提供粗略的总量控制。这个选择的限制是全局配额不能严格保证。

降级：提前定义可牺牲的功能和结果

降级需要回答两个问题：哪些功能可暂时停止，调用方将收到什么结果。云盘当时的可降级项来自前面各篇的实践：

  • 热点上报：第 6 篇中高峰期收到即返回、丢弃统计数据的开关；
  • 多端通知：通过 Kafka 异步处理后，消费者可以限速或暂停。前提是消息保留时间、积压容量和用户对延迟的容忍度都满足要求；
  • 聚合接口的非关键字段：第 5 篇的字段级降级，在超时或开关开启时返回空值；
  • 缓存旧值：第 11 篇的兜底路径。它仅适用于允许陈旧数据的展示口径，并需要明确旧值的有效期和失效处理。

开关需要在故障发生前配置并验证。云盘当时的规则是：配置可热更新，开启开关不依赖发版；在正常时期演练开关，检查开启后的返回结果、流量变化和监控信号；按影响程度分级，先停止上报和动态摘要，再处理通知延迟或旧缓存。核心读写路径不在当时的降级清单中。第 6 篇将通知延迟描述为“晚一点、乱一点，天不会塌”，第 11 篇区分了展示口径和决策口径；这里的工程含义是，只有业务允许延迟、缺失或陈旧结果时，才可以将其作为降级结果。

高峰流量中的处理记录

IM 融合后，云盘服务端经历过几次流量高峰，量级按惯例未公开。以下是当时的复盘记录，不应据此推导其他系统的容量结论。

融合切流后的头几个工作日，图片消息的全量流量进入鉴权和元数据接口。第 10 篇的容量评估提前确定了机器数，入口限流阈值在这次切流中没有触发，监控曲线保持平稳。第 9 篇中下载链路下沉到 nginx+lua，Java 只保留控制面处理，减少了下载请求经过的服务跳数和对应依赖。

第 11 篇的热点 key 失效事故中，热点 key 的缓存失效后，回源流量集中到数据库。快慢线程池隔离将影响限制在文件操作池，入口限流拒绝了超额请求，大盘接口的 RT 在当时的监控中没有明显变化。隔离的作用是限制资源竞争，不表示受影响的文件操作一定成功。

一次外部热点事件中，分享内容被集中访问，单接口流量在短时间内增加数倍。入口限流快速拒绝超额请求，动态摘要的降级开关减少了聚合接口负载，主功能在当时的观察中保持可用。从告警到开启开关用了几分钟，不需要发版或重启。这说明配置化开关缩短了人工处置时间，但仍取决于告警、值守和操作流程。

这些事件中，部分请求会被拒绝、超时或降级。处理目标是将影响限制在可预期范围内，并通过监控确认核心路径的成功率、延迟、拒绝率和资源池使用率。整体 RT 或单一“大盘”指标不能说明链路成功率。

当时的不足：没有自动熔断

当时的方案没有自动熔断。下游持续故障时，超时会让单次调用在限定时间内失败，限流可以保护入口，但调用仍会反复发往故障依赖，并消耗线程、连接和超时预算。

熔断器通常根据滚动窗口中的失败比例、慢调用比例或连续错误判断是否打开。打开后，调用直接快速失败或走预定义的回退路径；经过等待窗口后进入半开状态，只允许受限数量的探测请求。探测成功或失败达到配置条件后，再关闭或重新打开。阈值、统计窗口、半开探测量和回退结果需要结合依赖类型、调用量和重试策略验证。

2016 年，Netflix Hystrix 已是开源框架。我当时读过它的 wiki，也在本地运行过 demo，但没有将它用于生产。原因是：线程池隔离、超时和限流已经由现有实现覆盖了一部分 Hystrix 的能力；熔断状态机的边界没有经过真实故障验证；服务端当时只有一两个人，引入框架也意味着需要承担配置、监控和排障成本。

没有自动熔断时，持续故障依赖人工开启降级开关。人工处置通常以分钟计，自动熔断可在满足统计条件后更快执行，但也可能因阈值配置错误造成误熔断。这个缺口是当时方案的明确限制。

系列涉及的检查项

十三篇文章覆盖成员变量的线程安全、超时、重试、限流和降级等问题。它们共同关注系统失效的条件，以及发生后如何限制影响范围。线程池、连接池、锁、Future、Kafka、GC、日志、IO、压测、缓存和分布式锁处理的边界不同。

从 Node.js、C# 转到 Java 后，我没有把已有经验当作结论。已有项目中的线程、连接、缓存和远程调用问题提供了排查方向，Java 的线程模型、JVM、框架行为和多实例部署仍需要单独学习和验证。系列中有些内容来自实际故障后的复盘，也有些内容是在项目可能遇到相同约束前提前阅读、写 demo 或压测后，再决定是否用于项目。第 1 篇的并发模型、第 2、3 篇的资源池隔离、第 5 篇的有界等待、第 10 篇的容量评估，以及本篇的可用性措施，构成的是同一套检查路径。

可用性措施不会消除失败。设计时需要同时考虑依赖延迟、容量、幂等约束、资源池上限和业务结果，并通过故障演练和指标验证。对于请求链路，至少需要持续观察核心路径的成功率、超时率、重试次数、拒绝率、熔断状态、线程池与连接池饱和度，以及降级结果是否符合业务约束。
